# Исследование продукта для MVP «Запись на звонок»

Дата исследования: 11 октября 2026 года

## Краткий вывод

Минимальный продукт должен закрывать один сквозной цикл: владелец создаёт тип встречи и задаёт своё рабочее время, гость открывает публичную страницу, выбирает свободный 30-минутный слот, оставляет контактные данные и подтверждает запись, после чего владелец видит новую встречу в списке предстоящих.

Главная ценность Cal.com в этом сценарии — не сам календарь, а понятная последовательность состояний: тип встречи → дата → время → данные гостя → подтверждение. Для нашего проекта нужны только эти состояния и защита от двойного бронирования. Авторизация, внешние календари, видеоконференции, уведомления, команды, платежи и перенос встреч в MVP не входят.

## 1. Исходные ограничения проекта

Из «Описание проекта.docx» следуют обязательные ограничения:

- продукт — упрощённый сервис бронирования по мотивам Cal.com;
- владелец публикует доступное время;
- гость выбирает свободный слот и записывается на звонок;
- владелец видит список предстоящих встреч;
- авторизации, личных кабинетов и интеграций с внешними календарями нет;
- основной сценарий должен быть законченным и пригодным для развёртывания в облаке.

Есть расхождение между текстом и макетом: в тексте указаны слоты по 30 минут, а на одном из примеров показана встреча на 15 минут. Для MVP принимается правило из текста: **длительность каждой встречи фиксирована и равна 30 минутам**. Выбор длительности гостем и произвольная длительность типа встречи не реализуются.

Отсутствие авторизации означает, что разделы владельца и гостя разделяются только маршрутами и интерфейсом. Это допустимо для учебного MVP, но не является защитой данных и не подходит для реального публичного сервиса без последующего добавления контроля доступа.

## 2. Что изучено в Cal.com

### 2.1. Создание типа встречи

По актуальному руководству Cal.com пользователь открывает раздел типов встреч, нажимает `New`, выбирает вид события и задаёт основные параметры: название, описание и длительность. Затем выбирается расписание доступности и при необходимости настраиваются дополнительные вопросы, место встречи, ограничения и напоминания.

Для персонального сценария ядро типа встречи состоит из:

- названия;
- описания;
- уникального адреса страницы;
- длительности;
- правил доступности.

Командные типы, round-robin, несколько организаторов, разные места встречи и дополнительные правила не нужны для нашего MVP.

Источник: [руководство Cal.com по типам встреч](https://cal.com/blog/event-types-guide-calcom).

### 2.2. Публичная страница владельца

В текущем интерфейсе Cal.com публичная страница владельца показывает имя, описание профиля и карточки доступных типов встреч. Карточка содержит название, краткое описание и длительность. Нажатие на карточку открывает календарь конкретного типа.

Проверенный путь:

1. Открыть публичную страницу владельца.
2. Просмотреть доступные типы встреч.
3. Выбрать карточку типа встречи.
4. Перейти на его страницу бронирования.

Пример: [публичная страница Cal.com с типом встречи](https://cal.com/graeme.j?redirect=false).

### 2.3. Страница бронирования

На странице конкретного типа Cal.com показывает:

- владельца и название встречи;
- описание;
- длительность;
- место встречи, если оно настроено;
- часовой пояс;
- календарь месяца;
- недоступные даты в выключенном состоянии;
- свободное время выбранного дня.

После выбора времени интерфейс переходит к форме записи. В стандартном варианте форма содержит имя, email, необязательное примечание и возможность добавить гостей. Рядом остаётся сводка: дата, интервал, длительность и часовой пояс. До отправки можно вернуться назад.

В документации компонент бронирования описан как последовательность состояний: загрузка → выбор даты → выбор времени → форма → успех или ошибка. Эта модель хорошо подходит для нашего MVP.

Источники: [документация Booker](https://cal.com/docs/platform/atoms/booker), [демонстрационная страница бронирования](https://app.cal.com/rajbreno-demo/in-person?embed=&embedType=inline).

### 2.4. Управление встречами владельцем

В Cal.com владелец открывает раздел Bookings. Полный продукт делит встречи на предстоящие, неподтверждённые, повторяющиеся, прошедшие и отменённые. Для нашего сценария достаточно только предстоящих подтверждённых встреч, отсортированных от ближайшей к более поздним.

Источники: [обзор раздела Bookings](https://cal.com/blog/a-complete-walkthrough-of-cal-com-s-booking-dashboard-its-key-features), [FAQ Cal.com](https://cal.com/faq).

## 3. Роли и задачи пользователей

### Владелец календаря

Хочет один раз настроить предложение и доступность, затем получать записи без ручного согласования времени.

Его задачи:

- создать и исправить тип встречи;
- задать часы, в которые можно бронировать звонки;
- открыть публичную страницу и проверить результат;
- скопировать или передать ссылку;
- видеть ближайшие записи и данные гостей.

### Гость

Хочет понять назначение встречи, быстро найти подходящее время и получить явное подтверждение записи.

Его задачи:

- выбрать тип встречи;
- увидеть только реально доступные даты и время;
- указать имя и email;
- проверить выбранный интервал;
- завершить запись или понятным образом исправить ошибку.

### Система

Отвечает за расчёт свободных слотов, сохранение записи и предотвращение пересечений.

## 4. Карта минимального продукта

### Публичная часть

- `/` — короткая главная страница с кнопкой «Записаться»;
- `/book` — публичный список типов встреч;
- `/book/:slug` — календарь и форма бронирования выбранного типа;
- `/book/:slug/success` — подтверждение успешной записи.

Главную страницу и список типов можно объединить, если это ускоряет реализацию.

### Раздел владельца

- `/manage/event-types` — список типов встреч и переход к публичному просмотру;
- `/manage/event-types/new` — создание типа встречи;
- `/manage/event-types/:id/edit` — редактирование типа;
- `/manage/availability` — единое недельное расписание владельца;
- `/manage/bookings` — список предстоящих встреч.

Название `/manage` подчёркивает назначение раздела, но не создаёт ложного ощущения, что он защищён авторизацией.

## 5. Сквозные пользовательские пути

### Путь A. Создание типа встречи

**Предусловие:** владелец открыл раздел управления типами.

1. Владелец нажимает «Создать тип встречи».
2. Система показывает форму.
3. Владелец вводит название и необязательное описание.
4. Система показывает фиксированную длительность «30 минут» без возможности её изменить.
5. Система автоматически формирует `slug` для публичной ссылки.
6. Владелец сохраняет форму.
7. Система проверяет данные, создаёт тип и возвращает к списку.
8. В списке появляется карточка с действиями «Редактировать» и «Открыть страницу бронирования».

Минимальные поля:

| Поле         | Обязательность | Правило                                                               |
| ------------ | -------------- | --------------------------------------------------------------------- |
| Название     | Обязательно    | После удаления пробелов не пустое, рекомендуемый предел 3–80 символов |
| Описание     | Необязательно  | До 500 символов                                                       |
| Длительность | Системное      | Всегда 30 минут                                                       |
| Slug         | Системное      | Формируется из названия, уникальность обеспечивается системой         |

Состояния и ошибки:

- пустое название — сообщение под полем, сохранение не выполняется;
- слишком длинное название или описание — понятная ошибка с лимитом;
- совпавший `slug` — система добавляет безопасный суффикс или просит выбрать другой адрес;
- ошибка сервера — введённые данные остаются в форме, доступна повторная попытка;
- двойное нажатие «Сохранить» — создаёт только одну запись.

### Путь B. Настройка доступности

Для MVP предлагается одно глобальное недельное расписание, общее для всех типов встреч.

1. Владелец открывает «Доступность».
2. Для каждого дня недели включает или выключает доступность.
3. Для включённого дня задаёт один интервал начала и окончания, например 09:00–18:00.
4. Выбирает или видит зафиксированный часовой пояс приложения.
5. Сохраняет расписание.
6. Система делит интервалы на 30-минутные слоты и использует их на публичной странице.

Правила:

- время начала должно быть раньше времени окончания;
- интервал должен вмещать хотя бы один 30-минутный слот;
- слот создаётся только тогда, когда целиком помещается в интервал;
- начало слота выравнивается по получасовой сетке, например 09:00, 09:30, 10:00;
- прошедшие интервалы не показываются;
- горизонт бронирования для MVP — ближайшие 30 дней;
- разовые исключения для отдельных дат можно добавить позже.

Если расписание ещё не настроено, публичная страница не должна показывать выдуманные слоты. Она показывает состояние «Свободного времени пока нет».

### Путь C. Просмотр публичных типов встреч

1. Гость открывает `/book`.
2. Видит название сервиса или владельца и список опубликованных типов.
3. На каждой карточке видит название, описание и длительность 30 минут.
4. Нажимает на карточку и переходит в календарь.

Альтернативы:

- если тип один, допустим немедленный переход к его календарю;
- если типов нет, показывается пустое состояние без неработающей кнопки;
- прямая ссылка `/book/:slug` должна работать без предварительного посещения списка;
- неизвестный или скрытый `slug` приводит на понятную страницу «Тип встречи не найден».

### Путь D. Выбор даты и времени

1. Гость открывает страницу типа встречи.
2. Видит название, описание, длительность и часовой пояс.
3. Календарь открывается на текущем месяце.
4. Прошедшие даты и даты без свободных слотов недоступны.
5. Гость выбирает доступную дату.
6. Система показывает свободные 30-минутные интервалы этого дня.
7. Гость выбирает время.
8. Интерфейс переходит к форме и показывает сводку выбранной даты и времени.

Состояния:

- загрузка календаря и слотов;
- день со свободными слотами;
- день без свободных слотов;
- весь месяц без свободного времени;
- ошибка загрузки с кнопкой «Повторить»;
- переход к следующему месяцу в пределах горизонта бронирования.

### Путь E. Оформление записи

1. Гость видит сводку: тип встречи, дата, время, длительность и часовой пояс.
2. Вводит имя и email.
3. При желании добавляет примечание.
4. Нажимает «Подтвердить запись».
5. Кнопка блокируется, пока идёт запрос.
6. Сервер повторно проверяет доступность слота и атомарно создаёт запись.
7. Гость попадает на экран успеха.

Минимальная форма:

| Поле       | Обязательность | Правило                                           |
| ---------- | -------------- | ------------------------------------------------- |
| Имя        | Обязательно    | Непустое после удаления пробелов, до 100 символов |
| Email      | Обязательно    | Валидный формат, хранится без вывода в URL        |
| Примечание | Необязательно  | До 1000 символов                                  |

Экран успеха показывает:

- сообщение «Запись подтверждена»;
- название встречи;
- дату и интервал;
- часовой пояс;
- имя гостя;
- кнопку возврата к списку типов.

Email-письмо и ссылка на видеозвонок не обещаются, поскольку уведомления и интеграции не входят в MVP.

### Путь F. Просмотр предстоящих встреч владельцем

1. Владелец открывает `/manage/bookings`.
2. Система показывает только встречи, время начала которых ещё не наступило.
3. Встречи отсортированы по времени начала по возрастанию.
4. Для каждой встречи видны дата, интервал, тип, имя, email и примечание гостя.
5. После новой записи список при повторном открытии или обновлении страницы содержит встречу.

Обязательные состояния:

- загрузка;
- пустой список «Предстоящих встреч пока нет»;
- список встреч;
- ошибка загрузки с повторной попыткой.

Отмена, перенос, подтверждение владельцем, фильтры и просмотр истории не входят в P0.

### Путь G. Редактирование типа встречи

Редактирование нужно, чтобы владелец мог исправить опечатку без пересоздания типа.

1. Владелец выбирает тип в списке.
2. Открывает редактирование.
3. Меняет название или описание.
4. Сохраняет изменения.
5. Публичная страница показывает новые данные.

Существующие бронирования сохраняют связь с типом. Удаление типа не нужно в P0: оно создаёт лишние вопросы о существующих встречах. При необходимости после MVP лучше добавить деактивацию, которая скрывает тип от новых гостей, но не удаляет историю.

## 6. Критические пограничные сценарии

| Ситуация                                               | Ожидаемое поведение                                                                                |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Два гостя открыли один слот                            | Оба могут видеть его до отправки, но сохранить запись может только первый                          |
| Слот занят между выбором и подтверждением              | Второй гость получает сообщение «Это время уже занято» и возвращается к обновлённому списку слотов |
| Двойное нажатие кнопки подтверждения                   | Создаётся одна встреча, кнопка заблокирована во время запроса                                      |
| Один владелец и несколько типов встреч                 | Бронь любого типа блокирует этот интервал для всех типов                                           |
| Владелец изменил расписание, пока гость заполнял форму | Серверная проверка решает, допустим ли слот; устаревший слот не сохраняется                        |
| Гость открыл прошедший слот по старой ссылке           | Форма не подтверждается, предлагается выбрать новое время                                          |
| Нет доступных дат в горизонте 30 дней                  | Показывается честное пустое состояние без пустого календаря                                        |
| Невалидный email                                       | Ошибка показывается рядом с полем до отправки                                                      |
| Сервер временно недоступен                             | Данные формы сохраняются на экране, доступна повторная попытка                                     |
| Страница обновлена на шаге формы                       | Допустимо вернуться к календарю; уже созданная бронь не должна дублироваться                       |
| Очень длинный текст или HTML в полях                   | Сервер применяет лимиты и экранирует вывод, скрипты не выполняются                                 |
| Часовой пояс не определён                              | Используется настроенный часовой пояс приложения и явно показывается пользователю                  |

## 7. Бизнес-правила свободного слота

Свободный слот — это 30-минутный интервал, который одновременно удовлетворяет всем условиям:

1. находится внутри включённого интервала недельного расписания;
2. начинается в будущем;
3. попадает в горизонт бронирования 30 дней;
4. не пересекается с локальной бронью этого единственного владельца;
5. по-прежнему свободен в момент серверного подтверждения.

Так как владелец один и длительность фиксирована, в базе достаточно запретить две активные брони с одинаковым `start_at` независимо от типа встречи. Проверка только в интерфейсе недостаточна: окончательная гарантия должна быть на сервере и в ограничении базы данных.

## 8. Минимальная модель данных

### EventType

- `id`;
- `title`;
- `slug` — уникальный;
- `description` — необязательный;
- `duration_minutes` — всегда 30;
- `is_active` — можно подготовить в модели, даже если переключатель появится позже;
- `created_at`, `updated_at`.

### AvailabilityRule

- `id`;
- `weekday` — 1–7;
- `is_enabled`;
- `start_time`;
- `end_time`;
- `timezone` — единый для расписания.

Для P0 достаточно не более одного интервала на день. Обеденные перерывы и несколько интервалов можно добавить позже.

### Booking

- `id`;
- `event_type_id`;
- `start_at`;
- `end_at`;
- `guest_name`;
- `guest_email`;
- `guest_note` — необязательный;
- `created_at`.

В P0 статус можно не хранить, поскольку существует только подтверждённая запись и нет отмены. Если статус добавляется заранее, единственным рабочим значением будет `confirmed`.

## 9. Функциональные критерии приёмки

1. **Создание типа.** Если владелец ввёл корректное название и сохранил форму, новый тип появляется в разделе управления и на публичной странице.
2. **Валидация типа.** Если название пустое, тип не создаётся, а рядом с полем показывается причина.
3. **Расписание.** Если понедельник настроен на 09:00–11:00, система формирует слоты 09:00, 09:30, 10:00 и 10:30.
4. **Недоступные даты.** Если на дату нет хотя бы одного свободного слота, её нельзя выбрать в календаре.
5. **Бронирование.** Если гость выбрал свободный слот, ввёл валидные имя и email и подтвердил форму, запись сохраняется и показывается экран успеха.
6. **Исчезновение слота.** После успешной записи этот слот больше не отображается ни для этого, ни для другого типа встречи владельца.
7. **Гонка запросов.** Если два запроса одновременно бронируют одно время, успешен только один; второй получает контролируемый конфликт, а не ошибку сервера.
8. **Предстоящие встречи.** Новая встреча появляется у владельца в хронологически отсортированном списке.
9. **Прямая ссылка.** Корректный `slug` открывает нужный тип, а неизвестный показывает понятную страницу 404.
10. **Пустые состояния.** Отсутствие типов, расписания, слотов и встреч объясняется отдельными сообщениями с подходящим следующим действием.

## 10. Приоритеты

### P0 — обязательно для минимального законченного продукта

- список, создание и редактирование типов встреч;
- фиксированная длительность 30 минут;
- одно глобальное недельное расписание и один часовой пояс;
- публичный список типов и прямые ссылки;
- календарь доступных дат и слотов;
- форма с именем, email и необязательным примечанием;
- подтверждение записи;
- серверная защита от двойного бронирования;
- список предстоящих встреч владельца;
- загрузка, пустые состояния, валидация и понятные ошибки;
- адаптивность для телефона и управление с клавиатуры.

### P1 — следующее расширение

- деактивация типа встречи;
- копирование публичной ссылки;
- исключения доступности для отдельных дат;
- несколько интервалов доступности в день;
- карточка деталей встречи;
- отмена или перенос;
- история прошедших встреч.

### Не входит в текущий проект

- регистрация, вход и разграничение прав;
- несколько владельцев и личные кабинеты;
- Google Calendar, Outlook и другие внешние календари;
- Zoom, Google Meet и автоматическая генерация ссылок;
- email, SMS и push-уведомления;
- разные длительности и выбор длительности гостем;
- команды, round-robin и коллективные встречи;
- повторяющиеся встречи;
- платежи;
- подтверждение записи владельцем;
- гости и кастомные вопросы;
- аналитика, фильтры и поиск;
- полноценный выбор часового пояса.

## 11. UX-рекомендации

- На каждом шаге показывать, что уже выбрано: тип → дата → время.
- Недоступные даты делать визуально и технически выключенными, а не позволять клик с последующей ошибкой.
- После выбора слота оставлять дату и интервал рядом с формой, чтобы гость не потерял контекст.
- Использовать одну основную кнопку на экран: «Создать тип», «Сохранить доступность», «Подтвердить запись».
- Не обещать письмо, календарное событие или ссылку на звонок, если их нет.
- Показывать часовой пояс рядом со временем на календаре, в форме и на экране успеха.
- Не передавать имя или email в адресной строке.
- Сообщение о конфликте слота должно возвращать к выбору времени без потери введённых имени, email и примечания.

## 12. Риски и решения

| Риск                                              | Решение для MVP                                                                    |
| ------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Двойное бронирование при одновременных запросах   | Транзакция и уникальное ограничение на время начала                                |
| Разные представления времени на клиенте и сервере | Хранить момент времени однозначно, показывать один настроенный часовой пояс        |
| Несогласованность нескольких типов встреч         | Считать занятость общей для единственного владельца                                |
| Незащищённые страницы владельца                   | Явно считать приложение учебным демо; перед реальным запуском добавить авторизацию |
| Пустой продукт после первого открытия             | Добавить понятные пустые состояния и последовательные CTA                          |
| Слишком широкий объём                             | Не реализовывать функции из раздела «Не входит» до завершения P0                   |

## 13. Рекомендуемый порядок реализации

1. Модель типов встреч и экран управления.
2. Глобальное недельное расписание.
3. Расчёт 30-минутных слотов на сервере.
4. Публичный список типов и календарь.
5. Форма и атомарное создание брони.
6. Экран успеха.
7. Список предстоящих встреч.
8. Пограничные состояния, адаптивность и сквозные тесты.

Такой порядок сначала создаёт источник данных и правила доступности, затем пользовательский путь гостя и только после этого вспомогательные экраны. Главный сквозной тест проекта: создать тип → настроить доступность → забронировать слот как гость → увидеть встречу у владельца → убедиться, что занятый слот исчез.
